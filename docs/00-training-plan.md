# 手掌检测与左右手识别训练计划

## 任务定义

本项目的训练目标是识别图像中人手的位置，并输出人的解剖学左手或右手。它不是掌纹识别、身份识别、关键点回归或手势分类。

每个最终检测结果包含框、置信度和类别：`left_palm` 或 `right_palm`。这里的框定位 MediaPipe 定义的掌部区域，不包括整只手的全部指尖；后续掌纹识别仍须核对掌面朝向和掌纹图像质量。

左右类别始终按人的解剖学方向定义，不按画面左右或摄像头镜像预览定义。任何数据增强、推理预处理和显示层都必须遵守此规则。

## 第一版模型范围

第一版基线固定为 **NanoDet-Plus-m，320 x 320 静态输入，2 类检测头**。选择它是因为模型紧凑、前向网络和后处理可以分离，便于导出静态 ONNX 并评估 Ascend 310B 路径。

训练服务器的职责是数据准备、训练、验证和 ONNX 导出。20T 开发板的职责是 ATC、ACL 数值一致性、真实任务质量和性能验证。训练收敛、ONNX 可运行、ATC 成功、ACL 一致性、任务质量和性能是独立证据，任何一项均不能代替另一项。

## 数据合同

### 类别与标注

COCO 类别 ID 固定如下，训练、验证、导出、解码和开发板后处理均不得重排：

| COCO `id` | 内部索引 | 类别名 | 含义 |
| --- | ---: | --- | --- |
| 1 | 0 | `left_palm` | 人的左手掌部，掌心、手背和侧面均可 |
| 2 | 1 | `right_palm` | 人的右手掌部，掌心、手背和侧面均可 |

使用 COCO `xywh` 像素坐标。框表示掌部区域，不是整只手的最小外接矩形；不包含无关的大面积前臂、躯干或手持物。

标注规则：

1. 能可靠判断左右手且可见面积足够时必须标注。
2. 双手重叠时标为两个实例；遮挡时按可见区域标框，`iscrowd=0`。
3. 强遮挡、运动模糊或尺寸过小而不能可靠区分左右手的实例标为 `ignore` 审核样本，不伪造为任一类别。
4. 镜面、屏幕、海报和照片中的人手默认不标注；产品确需检测时，先修订并版本化标注规则。
5. 训练数据应覆盖掌心、手背、侧面、张开、握拳、旋转、不同肤色、手套、首饰、遮挡、低照度和运动模糊。

### 来源、隐私和许可

每个数据源在 `data/manifests/` 中维护不含图像内容的清单，包含来源、采集日期、使用授权、主体 ID、会话/视频 ID、设备、分辨率、是否镜像、图像 SHA-256 和标注版本。

不把可识别个人、原始视频或未确认授权的数据提交到 Git。公开数据应保留上游许可证和再分发约束；自采数据应保存授权和保留策略。

### 数据划分

按 **主体 ID + 采集会话/视频** 划分 train、val、test，严禁将同一人、同一视频片段、相邻帧或同一镜像增强源分入多个集合。推荐初始比例为 70% / 15% / 15%，但独立测试集和跨场景覆盖优先于比例。

另建一份不参与调参的现场验收集，覆盖目标摄像头、安装高度、光照、背景、多人、远近距离和左右手交叉。模型冻结后才允许使用该集合。

### 训练前数据检查

在开始正式训练前生成并保存 JSON 报告：

- COCO JSON 可解析，图片、标注和类别引用完整且 ID 唯一。
- bbox 宽高为正，未越界，面积正确。
- 报告每个 split 的类别数、目标尺寸分布、每图目标数、主体数和会话数。
- 检查损坏图片、空文件、重复图像哈希和跨 split 的主体/会话泄漏。
- 每类至少复核 10% 且不少于 100 个实例，记录左右颠倒、漏标、框不紧和歧义数。
- 以训练时的 resize/letterbox 预处理可视化至少 100 张图，确认小目标、边缘目标和重叠目标未被裁掉或扭曲。

## 训练阶段

### 阶段 0：冻结可复现输入

每次训练运行记录项目 Git commit、上游 NanoDet commit、配置 SHA-256、数据和 split SHA-256、预训练权重 URL/版本/许可证/字节数/SHA-256，以及 OS、Python、PyTorch、CUDA、cuDNN、GPU 和驱动版本。

训练环境必须使用隔离的 conda 或 venv，并由锁定依赖文件重建。未经明确批准，不修改系统 Python、系统 CUDA 或开发板 CANN 环境。

### 阶段 1：数据管道冒烟

1. 选取 20 到 50 张已经复核的图像建立调试集。
2. 跑通读取、增强、损失、单 batch 反向传播、checkpoint 保存和 COCO 评估。
3. 对调试集过拟合，确认损失下降且可视化中的框和左右类别正确。
4. 默认关闭水平翻转。只有增强实现能同步交换 `left_palm` 与 `right_palm`，并有自动化测试时，才可启用。
5. 输出原图、增强图、标注和预测的叠加图供人工审查。

阶段 1 失败时，只修复数据合同、类别映射或增强流程，不进入长训练。

### 阶段 2：NanoDet-Plus-m 320 基线

| 项目 | 初始选择 | 约束 |
| --- | --- | --- |
| 架构 | NanoDet-Plus-m | 两类检测头 |
| 输入 | 320 x 320 静态形状 | 与后续静态 ONNX 目标一致 |
| 预训练 | 公开 COCO 预训练模型 | 记录固定版本和哈希 |
| 训练轮数 | 当前基线 150 epoch | 按验证集最佳 checkpoint 选择 |
| 优化器与学习率 | 继承上游基线 | 按有效 batch size 缩放且记录全部改动 |
| 增强 | resize、随机尺度/仿射、颜色扰动、轻度模糊/压缩 | 不得破坏左右标签语义 |
| checkpoint | 验证集主指标最佳 | 不能以训练损失最低或最后一轮替代 |

一次实验只改变一项或少量能解释的变量，例如输入尺寸、增广强度、学习率或困难样本比例。所有变更必须基于验证集错误证据，不能同时改变模型、数据和超参数。

### 阶段 3：有限消融与定版

按以下顺序执行，所有候选均使用同一冻结测试集：

1. 比较 320 与 416 输入的召回、模型大小和后续 310B 时延。
2. 比较禁用翻转与已验证类别交换的翻转，重点检查左右手混淆。
3. 比较常规增广与目标场景困难样本增广，检查低照、模糊和遮挡子集。
4. 仅在性能确有必要时比较 NanoDet-Plus-m 与更小变体。

若已经查看测试集结果后继续调参，应将该集合降级为验证集并重新冻结独立测试集。

## 评估和候选准入

报告同时输出 COCO 指标与项目任务指标：

| 指标 | 说明 | 第一版候选建议门槛 |
| --- | --- | --- |
| `AP50` | IoU=0.50 的平均 AP | >= 0.90 |
| `mAP50:95` | COCO 0.50 至 0.95 平均 AP | 记录并比较版本 |
| 每类 `AP50` | 左手、右手分别报告 | 两类不可合并隐藏 |
| 正确左右手率 | IoU>=0.50 的匹配框中类别正确比例 | >= 0.95 |
| 漏检率 | 固定阈值下未匹配真值的比例 | 按场景分组报告 |
| 重复检出率 | 单一真值被多个最终 NMS 框命中 | 报告并排查 |

这些数值是进入开发板验证的建议阈值，而非已测结论。产品负责人应在测试集冻结前确认最终要求。

评估报告必须包含总表、每类 AP/AR、PR 曲线、混淆矩阵、固定 score/NMS 阈值、按目标像素尺寸/光照/遮挡/主体/设备分组的结果，以及漏检、错左右、定位偏差和重复检出的受控样例清单。

## ONNX 与 Ascend 310B 验证

导出目标为 `1 x 3 x 320 x 320` 的静态 ONNX。导出前固定并记录颜色顺序、归一化、缩放/填充、输入名/形状、输出张量、DFL 解码、score 阈值和 NMS 参数。优先让 ONNX 只包含网络前向图，把不易转换的解码和 NMS 放在宿主侧实现。

流程：

1. 用最佳 checkpoint 的 eval 图导出 ONNX，执行 ONNX checker 与 shape inference。
2. 用至少 20 张固定代表图比较 PyTorch 与 ONNX Runtime 原始输出及解码后检测；记录误差、框 IoU 和类别一致率。
3. 生成模型卡：输入输出合同、预后处理、类别表、权重/ONNX SHA-256、导出命令、软件版本和许可证。
4. 将 ONNX、日志和模型卡交给 20T 开发板的独立 ATC 任务。
5. 在开发板分别尝试默认精度和 `allow_fp32_to_fp16` 路径；记录 ATC 命令、CANN/驱动/固件版本、OM SHA-256、失败算子和日志。
6. 对每个成功 OM，以完全相同的预处理和宿主后处理比较 ONNX/ACL 输出，然后重新计算任务质量和性能。

混合精度可转换不代表质量通过。数值差异应按输出张量、预处理、布局、精度策略、DFL 解码和 NMS 定位，不得靠更换测试集或随意调阈值掩盖。

## 实验记录、风险与交付

每个实验使用不可变 run ID，例如：

```text
nanodet-plus-m-320-palm__data-v001__cfg-<shortsha>__seed-42__YYYYMMDD-HHMM
```

run 目录至少保存 `run.json`、配置副本、训练日志、最佳 checkpoint 元数据、验证指标、数据/代码哈希和失败原因。未完成 ATC、ACL 数值、任务质量和性能证据前，模型只能称为训练候选，不能称为已适配 310B。

重点风险及处置：

| 风险 | 处置 |
| --- | --- |
| 镜像导致左右标签反转 | 默认禁用翻转；验证类别交换并增加单元测试后再启用 |
| 视频帧泄漏 | 以主体和会话划分，并检查交集与重复哈希 |
| 训练集质量高但现场失败 | 补采目标场景数据，不在现场验收集上反复调参 |
| ONNX 与原模型后处理不一致 | 固定输出合同，分别对原始输出和解码结果进行比较 |
| ATC 某精度路径失败 | 将失败限定为该模型、版本和参数组合，保存日志，不伪造 OM |
| 混合精度漂移 | 先定位张量和后处理差异，重新评估质量后再决定是否采用 |

训练 agent 的最低完成清单：

- [ ] 数据合同、类别表、隐私和许可证信息已记录。
- [ ] 无泄漏的 train/val/test split 已生成并审查。
- [ ] 数据检查、可视化和小集过拟合已完成。
- [ ] 可复现的 NanoDet 配置、训练/评估/导出脚本及测试已提交。
- [ ] 基线训练、独立测试和错误分析已完成。
- [ ] 固定 320 ONNX、模型卡和哈希已生成。
- [ ] 310B 转换、ACL 数值、任务质量和性能作为独立任务记录。
